# Phase 18 — CSRF protection

Audience: the developer or auditor who maintains the site. Date: 22 November 2026.

## CSRF types considered

| Type | What the attacker tries | Defence |
|---|---|---|
| Form POST from another site | An auto-submitting `<form>` that posts to `/api/admin/...` | Auth cookies are `SameSite=Strict` (not sent cross-site); the Origin check refuses foreign origins; the CSRF header is missing |
| JSON with a "simple" content type | `fetch` with `text/plain` and a JSON body to avoid a CORS preflight | JSON APIs require `Content-Type: application/json` (415 otherwise); the custom `X-CSRF-Token` header forces a preflight that is never allowed |
| Login CSRF | Signing the victim into the attacker's account | Login and all pre-sign-in auth steps need a token bound to an httpOnly, SameSite=Strict nonce cookie |
| Logout CSRF | Logging an admin out from another site | Logout is POST only and needs the token |
| Cookie tossing / subdomain | A sibling subdomain sets a cookie the site then trusts | `__Host-` prefix on session and nonce cookies in production (no Domain, Path=/, Secure); the refresh cookie is `__Secure-` with `Path=/api/auth` |
| Clickjacking | Framing the admin and tricking clicks | `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` |

## How the token works

- `GET /api/auth/csrf` returns a token. Signed in: `HMAC("sid:" + session id)`. Not signed in:
  `HMAC("pre:" + nonce)` where the nonce lives in `gi_pre` (`__Host-gi_pre` in production), httpOnly,
  SameSite=Strict, 2 hours.
- The browser keeps the token in memory only (scripts never read cookies) and sends it as
  `X-CSRF-Token` on every POST/PUT/PATCH/DELETE to `/api/admin/*` and `/api/auth/*`
  (`src/lib/client/adminFetch.js`, `src/hooks/useMediaUpload.js` for local uploads).
- `route()` in `src/lib/http.js` checks it before any handler runs (`src/lib/security/csrf.js`).
  A failure is `403 { code: "csrf" }`; the client fetches a fresh token once and retries.
- Rotation: starting a session clears the nonce cookie, and a new session has a new session id, so
  every sign-in gets a new token.

## Exempt routes and why

| Route | Why it is safe without the token |
|---|---|
| `POST /api/auth/refresh` | Only rotates the caller's own refresh cookie (SameSite=Strict, Path=/api/auth); nothing an attacker gains |
| `GET /api/auth/csrf` | Hands out the token; a GET with no side effect beyond setting the nonce cookie |
| `/api/public/*` (enquiry, newsletter, basket, consent, search) | No session involved; protected by the Origin check, Turnstile, honeypot and rate limits |

## GET requests that change state (reviewed)

| Route | Change | Why it is acceptable |
|---|---|---|
| `GET /api/public/newsletter/confirm` | Nothing any more (22 Nov 2026) | Old links only redirect to `/newsletter/confirm#t=…`; the page confirms with a same-origin **POST** when the person presses the button, so mail scanners that open links cannot subscribe anyone |
| `GET /api/cron/purge` | Deletes trash older than 30 days | Needs `CRON_SECRET` as a Bearer token; 404 otherwise |

No other GET handler writes to the database.

## Server Actions

The site has none. `next.config.mjs` still sets `experimental.serverActions.allowedOrigins` to the site's
own host, so a future Server Action keeps Next's origin check.

## Tests

`tests/unit/csrf.test.js`: missing/wrong/foreign-session token → 403; right token → allowed; cross-site
text/plain form → refused; reads never need a token; login needs the pre-session token and a planted
nonce fails; a new session clears the nonce; only refresh and the token endpoint are exempt.
E2E (`tests/e2e/*`) exercises the real browser flow: every sign-in, save, upload and logout carries the token.
