# Phase 20 — XSS and CORS lockdown

Audience: the developer or auditor who maintains the site. Date: 22 November 2026.

## XSS types considered

| Type | Example | Defence |
|---|---|---|
| Stored | A product name or article body containing `<script>` | Plain-text fields refuse `<` and `>`; rich text is sanitised with an allow-list on save and again on render; React escapes everything else |
| Reflected | `?q=<script>` echoed into a page | Pages never put query strings into HTML; search results are rendered by React (escaped) |
| DOM-based | Script reading `location.hash` into `innerHTML` | No `innerHTML`/`document.write` in client code; the only `dangerouslySetInnerHTML` uses are listed below and checked by a test |
| Mutation XSS | Markup that changes meaning after parsing (`<math><mtext>…`, `<noscript>` tricks) | sanitize-html allow-list drops the containers; payloads in `tests/unit/xss.test.js` |
| Via SVG | `<svg onload=…>` upload or inline | SVG uploads refused; `svg` not allowed in rich text |
| Via markdown | `[x](javascript:…)` | The site does not render markdown; such text stays text |
| Via URL | `javascript:`, `data:`, `vbscript:` links | Admin-entered links go through `safeHref` (site paths, https, mailto, tel); rich-text links allow http/https/mailto/tel only |

## Where HTML is injected on purpose (`dangerouslySetInnerHTML`)

| Use | Why it is safe |
|---|---|
| JSON-LD `<script type="application/ld+json">` (breadcrumbs, FAQ, products, articles) | `jsonLd()` escapes `<` and the JavaScript line separators, so the data cannot close the script tag |
| Rich text (pages, buying guides, articles) | `sanitizeRichText()` output only |
| Theme CSS in `<style id="gi-theme">` | Built by `themeToCss()` from validated colour values and an allow-list of fonts; a test feeds it `</style><script>` |

`tests/unit/xss.test.js` fails if any new `dangerouslySetInnerHTML` appears that is not one of these.

## Content-Security-Policy

Applied to every page by `next.config.mjs`, built by `src/lib/security/csp.js`:

```
default-src 'self'; script-src 'self' 'unsafe-inline' <Turnstile, Google Analytics, Clarity>;
style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: <Cloudinary, analytics>;
connect-src 'self' <Turnstile, analytics, Cloudinary upload API>; frame-src <Turnstile, Google Maps>;
frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'; upgrade-insecure-requests;
report-uri /api/csp-report
```

**Why no per-request nonce (decision, 22 Nov 2026).** Next.js can only add a nonce to pages rendered on
every request. This site prerenders its pages (Partial Prerendering) for speed; Next's own guide states
that nonce-based CSP is incompatible with that. Giving it up would make every page dynamic (slower,
costlier). Instead:

- `'unsafe-inline'` is allowed only for scripts, and only because Next's inline bootstrap needs it;
- every script file carries a Subresource Integrity hash (`experimental.sri`), so a tampered file is refused;
- user content cannot contain markup (see above), which is what an attacker would need;
- Trusted Types run in **report-only** (`Content-Security-Policy-Report-Only: require-trusted-types-for 'script'`),
  so any code path that writes HTML into the DOM shows up in `/api/csp-report` before it could be exploited.

`src/lib/security/csp.js` still supports a nonce + `'strict-dynamic'` policy; switch to it if the admin
is ever made fully dynamic.

Reports: `POST /api/csp-report` (classic and Reporting API formats), 8 KB cap, rate limited, logs only the
directive, blocked origin, page path and line (query strings dropped).

## CORS

- No route ever sends `Access-Control-Allow-Origin`; the browser therefore refuses to give any response
  to another website (deny by default, no `*`, never with credentials).
- Preflight (`OPTIONS`) requests to `/api/*` from another origin are answered `403` by the proxy with no
  CORS headers.
- Admin and auth APIs are same-origin only: Origin check, SameSite=Strict cookies, CSRF token (Phase 18).
- API responses carry `Cross-Origin-Resource-Policy: same-origin`; pages carry
  `Cross-Origin-Opener-Policy: same-origin`.
- Webhooks: none yet. When Brevo or Cloudinary webhooks are added they must verify the provider's
  signature (HMAC with a secret) before doing anything; origin headers are not trusted for webhooks.

## Tests

- `tests/unit/xss.test.js`: payload list against the sanitiser, JSON-LD escaping, `safeHref`, theme CSS,
  the `dangerouslySetInnerHTML` inventory, and the CSP builder.
- `tests/e2e/cors.spec.mjs`: a page on another origin cannot read public or admin APIs; preflights get no
  CORS grant; headers on pages and APIs.
