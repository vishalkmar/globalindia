# Phase 22 — Rate limiting and abuse control

Audience: the developer or auditor who maintains the site. Date: 22 November 2026.

## Limits

Sliding windows in `src/lib/security/rateLimit.js`: Upstash Redis in production (shared by every
serverless instance), an in-memory fallback in development and tests. Every refusal is a **429 with a
`Retry-After` header**.

| What | Limit | Key | Where |
|---|---|---|---|
| Login | 5 / 15 min per IP **and** 5 / 15 min per email | IP; hashed email | `/api/auth/login` |
| Failed passwords | 5 wrong → account paused; each new pause within 24 h doubles: 15, 30, 60 min … max 24 h | account | `src/lib/auth/login.js` (`nextLockMinutes`) |
| OTP verify | 5 wrong tries burn the code; 10 / hour per user | OTP row; user | `src/lib/auth/otp.js`, verify routes |
| OTP resend | 60 s cooldown, 5 / hour per user and purpose | OTP rows in the database | `issueOtp` |
| Password reset request | 3 / hour per IP and per email | IP; hashed email | `/api/auth/reset/request` |
| Public forms (enquiry, newsletter) | 5 / hour per IP (admin-set 1–20); enquiries also 5 / hour per email | IP; email | public routes |
| Public search | 60 / min per IP (admin-set 10–120) | IP | `/api/public/search` |
| Uploads | 30 files / hour per admin (admin-set 5–100) | admin | media sign route |
| Any `/api/*` call | 300 / min per IP (admin-set 60–1000) | IP | `src/proxy.js` |
| Emails to one address | 8 / hour, whatever sends them | hashed address | `sendEmail` in `src/lib/brevo.js` |

Auth limits **fail closed** if Redis is unreachable. The global API limit and the per-recipient email
limit **fail open**: they are a second layer, and closing them would take the whole API or every sign-in
email down with Redis.

## Admin control (todos 13, 16)

Settings → **Rate limits and blocked IPs** (super admin only):

- the four adjustable limits above, each held inside a safe range by the schema (`LIMIT_CAPS`);
- **blocked IP addresses and ranges** (IPv4/IPv6, CIDR). Blocked addresses get a plain 403 on every page
  and API from the proxy. Ranges wider than /8 (IPv4) or /16 (IPv6) are refused, and a list that
  contains the saving admin's own address is refused, so nobody locks the office out by mistake.

Values are read from the database with a 60-second copy per instance; saving clears the copy at once.

## Bots and email bombing (todos 14, 15)

- Every public form (enquiries, newsletter) checks Cloudflare Turnstile on the server, plus a honeypot
  and a minimum time to submit. Without Turnstile keys in production the forms refuse (fail closed).
- Per-recipient email cap (8 / hour) on top of the per-form limits stops anyone from using the site to
  flood a third party's inbox with codes, receipts or confirmation links.

## Logging (todo 17)

`ratelimit.hit` logs the limit name, size and window only. IPs and emails are never logged; where a
key must be stored it is an HMAC with `IP_HASH_SALT`.

## Cloudflare (outer layer, todo 12)

To set up once the domain is on Cloudflare (owner action, needs the account). Security → WAF →
Rate limiting rules:

| Rule | Match | Rate | Action |
|---|---|---|---|
| Admin sign-in | `http.request.uri.path in {"/api/auth/login" "/api/auth/verify-otp" "/api/auth/verify-totp" "/api/auth/verify-recovery" "/api/auth/reset/request"}` and method POST | 20 per 1 min per IP | Block 10 min |
| Public forms | `starts_with(http.request.uri.path, "/api/public/")` and method POST | 20 per 1 min per IP | Managed challenge |
| API flood | `starts_with(http.request.uri.path, "/api/")` | 600 per 1 min per IP | Block 1 min |

These are looser than the app's own limits on purpose: Cloudflare stops floods before they reach Vercel,
and the app applies the exact limits. Also turn on Bot Fight Mode and the managed WAF ruleset.

## Load test (todo 18)

`node scripts/load-limits.mjs http://localhost:3000` against a production build (`next start`): bursts
of public searches and logins from one client, checking that the 429 comes at the expected request and
carries `Retry-After`. `tests/unit/abuse.test.js` covers the same limits, the admin caps, IP matching,
the self-block guard, the email cap and the back-off.
