# Phase 21 — Object and function level authorization

Audience: the developer or auditor who maintains the site. Date: 22 November 2026.

## Cases considered

| Case | What an attacker tries | Defence |
|---|---|---|
| BOLA / IDOR | Change an id in the URL or body to reach someone else's record (another editor's enquiry, another person's session) | Records are looked up together with the caller's scope (`enquiryScope`, `userId` on sessions); out-of-scope ids answer **404**, the same as ids that do not exist |
| BFLA | Call an endpoint the role should not reach (users, audit log, security settings, cache, theme publish, permanent delete) | Every handler calls `requirePermission(action, resource)` from `src/lib/auth/guard.js`; the role matrix lives in `src/lib/auth/permissions.js` |
| Mass assignment | Send extra fields (`role`, `passwordHash`, `mfaSetupAt`, `email`, `spamScore`, `createdAt`) | Every body is a `z.strictObject`: unknown keys are a 400, and only the parsed fields are written |
| Privilege escalation | `{"role":"SUPER_ADMIN"}` on one's own account; changing someone else's MFA | Only `users:update` (super admin) may change roles; nobody can change their own role or disable themselves; the last active super admin cannot be demoted; MFA for another account is super admin only, and an authenticator app only by its owner |
| Trusting the client | Role or user id sent by the browser | The acting user always comes from the verified access token (`requireAdmin`), never from the request |
| Hidden buttons | Calling the API behind a button the UI hides | The UI hides by role for convenience only; the same checks run on the server (tests below call the handlers directly) |
| Proxy bypass | Skipping `src/proxy.js` (CVE-2025-29927 style) | The proxy only redirects for convenience; every page (`requireAdminPage` / `requirePermissionPage`) and every handler re-checks |
| Guessable ids | Walking `1, 2, 3…` | All ids are cuids; non-cuid ids are refused before any query |

## Role matrix (who may do what)

| Area | Viewer | Editor | Super admin |
|---|---|---|---|
| Content (pages, products, categories, media, enquiries, insights, industries, menus, header/footer, SEO and redirects) | read | read, create, update, delete, publish | all |
| Theme | read | read, prepare (create, update) | all, including **publish** (activate) |
| Business details | read | read | all |
| Users, MFA of other accounts, audit log, security settings (maintenance, uploads, enquiry rules, cache purge), permanent delete from trash | – | – | all |

The source of truth is `MATRIX` in `src/lib/auth/permissions.js`; `matrixMarkdown()` prints the exact
current table if this summary is ever in doubt.

## Enquiries: "assigned only" (todo 07)

Settings → Enquiries and spam → "Editors and viewers see only enquiries assigned to them" (super admin
only, off by default). When on, `enquiryScope(user)` adds `assignedToId = <me>` to **every** enquiry
query for anyone below super admin: inbox list (including a forced `?assigned=<someone else>`), CSV
export, header bell, dashboard counts, recent list and charts, admin search, detail, status/assignee
change and notes. The setting is read straight from the database, never from the page cache, because it
is an access decision.

## Denials are recorded and watched (todos 17, 18)

- `denyAccess(user, …)` in `guard.js` is the single way to refuse a signed-in admin. It writes an
  `authz.denied` audit row (action, resource, role, and the target id for MFA attempts), then throws 403.
  `requirePermission`, `requirePermissionPage`, `requireAdmin({ role })` and the in-handler checks
  (publish rights, trash, product import, other people's MFA) all go through it.
- `checkDenialBurst` (`src/lib/auth/notify.js`): when one admin reaches **10 denials in 15 minutes**,
  every active super admin gets one security email and a `security.authz_denial_burst` warning is logged.
  It fires once per burst, not once per denial.
- Signed-out callers get 401 before any input is checked (the revisions endpoints were changed to do this
  in this phase), so nothing about ids or records leaks to anonymous callers.

## Server Actions

The site has none (`"use server"` appears nowhere). If one is added it must call `requirePermission`
itself; `next.config.mjs` already limits Server Action origins to the site host.

## Tests

- `tests/unit/authz.test.js`
  - signed out × every method of every `/api/admin` route → 401 (found automatically, new routes included);
  - EDITOR × 13 super-admin-only calls → 403, each with one new `authz.denied` audit row;
  - escalation through `role` in the body, own role / own status, invalid role values;
  - mass assignment on users and enquiries;
  - IDOR on enquiries with "assigned only" (detail, update, notes, list, forced filter, bell, export,
    admin search), super admin unaffected, switch off restores access; other people's sessions; cuid ids;
  - the denial burst alert (one email per super admin) and in-handler refusals audited;
  - drafts and deleted products/categories never returned by the public search.
- `tests/unit/viewer-write.test.js`: VIEWER × every write method of every admin route → 403.
